How well do quantum compilers handle Boolean functions?

Many quantum algorithms use a classical Boolean function as a reversible oracle. This project measures how many gates eleven compilers need to turn such oracles into hardware circuits, on six qubit layouts, and checks every circuit by simulation. The benchmark runs again every month with the newest compiler releases.

Jannik Pflieger · Code and data on GitHub

Summary

  • The numbers in this text are from the run of 27 November 2026 (4,490 compile jobs, pinned versions). The charts and tables always show the newest run.
  • Compilers that see the Boolean function beat generic matrix synthesis by one to two orders of magnitude. For AND on 6 qubits the best function-based result is 49 two-qubit gates (MQT), against 902 to 1,824 for Qiskit's matrix input, Qibo, quilc, Cirq and PennyLane. Matrix synthesis grows like 4n, so it reaches only 6 to 10 qubits within the 600 s limit.
  • No compiler is best for every function. Qrisp's Gray synthesis gives the fewest gates for majority, comparator and random truth tables (for example 126 two-qubit gates for a random function on 7 qubits, against 446 for tket and 680 for Qrisp PPRM). MQT is best for AND and XOR, Qrisp PPRM for the adder. Qrisp's Gray synthesis is wrong for XOR and the adder with 4 or more qubits (96 wrong results), so its low counts only count where it is verified.
  • Real device layouts cost a factor of about 1.5 to 3 in two-qubit gates compared with full connectivity (median over all verified cases). On IBM heavy-hex the factor is 1.5 to 1.9 for most compilers and 2.5 to 3.1 for Qrisp (routed by Qiskit's Sabre pass) and MQT.
  • Estimated success probability follows the gate count. For a random function on 6 qubits on IBM heavy-hex it is 0.68 with Qrisp Gray, 0.32 with tket and 0.03 with Qiskit's expression input; most matrix-synthesis circuits are close to 0.
  • Helper qubits pay off strongly. A 13-control AND (14 qubits) needs 1,084 two-qubit gates in Qiskit without helpers and 72 with one clean helper qubit; with one helper that may be in any state (dirty) it needs 138.
  • Compared with the thesis (2022), Qiskit's AND and OR circuits got much smaller (AND on 10 qubits: 1,532 → 288 two-qubit gates), but XOR got much larger (6 qubits: 5 → 1,280), because the current Boolean oracle no longer recognises XOR terms.
  • Two compiler problems were found: the Qrisp Gray synthesis bug above, and in MQT QMAP 3.11 the default dynamic initial layout reports a wrong initial_layout (MQT's own checker QCEC confirms the mismatch). MQT is therefore run with the static initial layout. quilc returned 10 wrong circuits on grid, ring and Sycamore layouts; the one small case among them was correct when run again locally, so the cause is probably numerical.

Background

Boolean functions as quantum operations

A quantum computer can only apply reversible operations. A Boolean function f: {0,1}n → {0,1}m is therefore implemented with m extra output qubits:

|x, y⟩ ↦ |x, y ⊕ f(x)⟩

The inputs stay unchanged and each output qubit is flipped when its output bit is 1. As a matrix this is a permutation of the computational basis states. Such matrices have much more structure than an arbitrary unitary of the same size, so a good compiler should need far fewer gates for them.

What a compiler has to do

  1. Synthesis: express the operation in a fixed set of native gates (single-qubit rotations and CNOT or CZ).
  2. Mapping and routing: place logical qubits on physical qubits and insert SWAP operations when two qubits that must interact are not connected.
  3. Optimisation: remove or merge redundant gates.

Two-qubit gates are the main source of error on current hardware, so their number is the main metric. Depth, T-count, compile time, memory and an estimated success probability are reported as well.

Measurements and correctness check

  • Gate counts and depth of the compiled circuit, including SWAPs (counted as three two-qubit gates).
  • T-count: every single-qubit gate is written as RzRxRz. An angle that is an odd multiple of π/4 counts as one T gate, a multiple of π/2 is free (Clifford). Any other angle is counted separately as an arbitrary rotation, which a fault-tolerant computer would have to approximate with many T gates. No compiler here optimises for T-count.
  • Compile time and peak memory of the compile process (memory includes loading the library).
  • Each job runs in its own process with a time limit (600 s; BQSKit gets twice as long). When a size times out, larger sizes of the same series are not attempted.
  • Correctness: every circuit is simulated. With the initial and final qubit placement reported by the compiler, every basis input (or a random subset for large circuits) must map to the right output with a common phase, with infidelity below 10−6. Helper qubits must start and end in |0⟩. Wrong results are marked ✗ and left out of the charts. Circuits on more than 24 qubits are not simulated.

Hardware and noise

Fewer gates only matter if they lead to better results on hardware. As a simple estimate, the success probability of a circuit is the product of the gate fidelities, (1 − e1)N1 (1 − e2)N2, with N1, N2 the numbers of single- and two-qubit gates. Discussion

The main result of the thesis still holds: a compiler that knows it is compiling a Boolean function produces far smaller circuits than one that only sees the matrix. The gap grows with the number of qubits, since generic unitary synthesis needs on the order of 4n two-qubit gates, while the best Boolean synthesis for AND, OR, the comparator and the adder grows roughly linearly or quadratically.

Among the Boolean methods the choice of synthesis matters more than the choice of compiler. Functions with a short expression (AND, XOR, the adder) are compiled well by expression-based tools (MQT, Qiskit, Qrisp PPRM). Functions given only as a truth table, or with many product terms (majority, random functions), favour Qrisp's Gray synthesis, which uses phase rotations instead of Toffoli gates. That has a cost the two-qubit count does not show: its circuits need arbitrary-angle rotations, which are expensive on a fault-tolerant computer, while MQT and Qiskit produce Clifford+T circuits (see the T-count and rotation metrics).

MQT uses extra helper lines from its SyReC synthesis, so its circuits use more qubits than the others (for example 11 helpers for a random 3-input function). On restricted layouts these helpers have to be routed too, which is why MQT's layout overhead is larger than that of most other compilers.

Optimisation levels matter mainly on restricted layouts. On the fully connected layout Qiskit's levels 0 to 3 differ by at most 2 %; on heavy-hex level 0 needs a median of 1.9 times (up to 2.8 times) the two-qubit gates of level 3. For tket the highest level changes nothing for AND and OR, but saves up to 88 % for XOR, majority and the adder.

The estimated success probability is a simple model (independent gate errors, no idle or readout errors), but it shows the practical consequence: on today's devices only circuits with at most a few hundred two-qubit gates have a reasonable chance of giving the right answer, which rules out generic synthesis beyond about 5 qubits.

What could be improved

  • More synthesis methods for the same function. ESOP-based synthesis (as in the old tweedledum library or Caterpillar), LUT-based hierarchical synthesis, or exact synthesis for small functions would show how far the current compilers are from the best known circuits.
  • Phase oracles. Many algorithms (Grover, Deutsch-Jozsa) only need the phase version (−1)f(x), which saves the output qubit and often half of the gates.
  • Larger functions from real use, for example the arithmetic and control benchmarks of the EPFL suite or RevLib, instead of only synthetic functions.
  • Noise-aware compilation and real calibration data. The success estimate uses one representative error rate per platform. Daily calibration data, or a short run on real hardware, would show whether the ranking holds.
  • Fault-tolerant cost. Counting T gates after synthesising the arbitrary rotations (for example with gridsynth) would compare the Gray and Toffoli-based approaches fairly.
  • Statistics. Compilers with random choices (Sabre, quilc, BQSKit) should be run with several seeds and reported with a spread.

Limitations

  • The matrix input is limited to 12 qubits (a 4,096 × 4,096 matrix); in practice matrix synthesis stops at 6 to 10 qubits because of the 600 s time limit (1,200 s for BQSKit, which reaches only 4 to 5 qubits).
  • Each job has a memory limit of 3.5 GB (status "memory limit"); this ends, for example, Qiskit's XOR series at 15 qubits and quilc's larger cases. Peak memory includes importing the libraries (about 100 to 300 MB).
  • Circuits with more than 24 used qubits are not simulated (marked "not simulated"); circuits with more than about 16 qubits are checked on a random sample of inputs.
  • Helper qubits are checked only for the input |0⟩. Helpers declared as "dirty" are not tested with other starting states.
  • MQT synthesises from the Boolean expression with SyReC; its line-aware synthesis needs more helper lines than heavy-hex (57) or Sycamore (54) have for majority and random functions with 5 or more inputs.
  • quilc runs out of memory or heap at 7 to 9 qubits in many cases.
  • IonQ is modelled only by its error rates on the fully connected layout; its native gates (MS, GPi) are not used.
  • staq is not included, because its Python package (pystaq) has no installable release for current Python versions; building it from source was not part of this setup.
  • The Qrisp results on restricted layouts depend on Qiskit's Sabre routing, since Qrisp has no routing of its own.

Reproduce

Every run stores its results and exact package versions under results/runs/. To repeat a run locally:

python -m venv .venv && . .venv/bin/activate && pip install -r requirements.txt
python -m venv venvs/qrisp && venvs/qrisp/bin/pip install -r requirements-qrisp.txt
python -m venv venvs/mqt && venvs/mqt/bin/pip install -r requirements-mqt.txt
docker pull rigetti/quilc:1.26.0
python -m bench.run --list                                   # shard names
python -m bench.run --shard main/tket/line --out out.jsonl   # one shard
python -m bench.job mqt adder 4 heavy_hex                    # one job

The workflow .github/workflows/benchmark.yml runs all shards in parallel and can be started by hand with pinned or newest versions.
